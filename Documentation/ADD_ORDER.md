# Как добавить заказ без изменения C#

## Готовый пример
`CatalogExamples/orders_extended.json` = `orders_base.json` + один заказ в конце массива `orders`:
```json
{
  "id": "order_05_long_parking",
  "title": "После долгой стоянки",
  "complaint": "Машина три недели стояла во дворе. Сегодня стартер почти не крутит, лампы на панели тусклые.",
  "faultId": "weak_battery",
  "timeBudget": 35
}
```
Используется уже существующая причина `weak_battery` (решение: замена аккумулятора + контрольный замер = 25 мин из 35).

## Что сделать
1. Остановить Play.
2. Заменить файл `Assets/StreamingAssets/CarDiagnosis/orders.json` содержимым `CatalogExamples/orders_extended.json`
   (в Windows-сборке — `<ИмяИгры>_Data/StreamingAssets/CarDiagnosis/orders.json`, пересобирать не нужно).
3. Play → «Начать смену». Счётчик показывает «ЗАКАЗ 01 ИЗ 05».
4. Пройти заказы 1–4 (решения — в `USER_CHECK_15MIN.md`). После четвёртого кнопка «Следующий заказ» открывает заказ 5.
5. Ожидаемо в заказе 5: Аккумулятор → Мультиметр «10,5 В» → «Заменить аккумулятор» → Мультиметр «12,6 В» → Завершить → «Заказ выполнен», «Это был последний заказ смены» → «Итоги смены» с пятью строками.
6. Вернуть исходный каталог: скопировать `CatalogExamples/orders_base.json` в `orders.json`.

`DefaultCatalog.json` (резерв) менять не нужно: он используется только если основной файл неверен.

## Правила формата (проверяются при запуске)
- `formatVersion` = 1. Порядок заказов = порядок в массиве `orders`, не больше 8.
- Все `id` непустые и уникальные внутри своего списка.
- `faultId` заказа → существующая запись `faults`; `fixedBy` → существующий `repairs`; `nodeId`/`nodeIds` → существующие `nodes`, которые есть в сцене (`battery`, `alternator`, `engine`, `brakes`).
- Стоимости 1–120 мин; `timeBudget` 1–600 и не меньше минимального пути (верный ремонт + самая дешёвая проверка на том же узле).
- Проверок не больше 3, ремонтов не больше 5, всего действий не больше 7 (вмещается правая панель). Новая проверка или ремонт появится кнопкой автоматически.
- Тексты: только символы шрифта — латиница, кириллица, цифры, знаки ASCII и `Ё ё — · № « »`. Нельзя: `–` (короткое тире), `…`, `→`, `×`, «умные» кавычки `“ ”`.
- Длины: название до 48, жалоба до 220, подпись кнопки до 34, крупная строка наблюдения до 40, текст до 220 символов.
- При любой ошибке весь файл отклоняется, в Console — список ошибок, игра идёт на встроенном каталоге.

## Новая причина (тоже без C#)
Добавить в `faults` запись: `id`, `fixedBy` (существующий ремонт) и `observations` — что покажет каждая проверка на каждом узле
(`headline`, `text`, и при необходимости `fixedHeadline`/`fixedText` после верного ремонта). Для пар проверка+узел без записи
показывается нормальная картина из `baseline` или нейтральный текст проверки.
Новый узел сцены, новый тип механики или новая модель — уже не данные, а работа в Unity.

## RC2: тип заказа и шиномонтаж
- Поле `type` заказа: `diagnosis` (по умолчанию, можно не писать — каталоги RC1 остаются валидными) или `tire_service`.
- Поле `goal` (необязательно, до 160 символов) — цель в карточке заказа.
- Заказ `tire_service` не имеет `faultId`; его параметры берутся из общего раздела `tireService`:
```json
"tireService": {
  "wheelName": "Переднее левое колесо", "fromTire": "летняя", "toTire": "зимняя",
  "imbalanceSide": "наружная сторона диска",
  "removeCost": 5, "dismountCost": 8, "mountCost": 8, "spinCost": 3, "weightCost": 3, "installCost": 5, "controlCost": 3,
  "imbalanceGrams": 25, "weightOptions": [15, 25, 35]
}
```
- Правила: `fromTire` ≠ `toTire`; стоимости 1–120; 2–3 уникальных груза 5–200 г; `imbalanceGrams` — один из `weightOptions`;
  `timeBudget` не меньше минимального пути (при значениях выше — 38 мин). Раздел нужен, только если в каталоге есть заказ шиномонтажа.
- Шиномонтажный заказ можно ставить в любое место списка (`CatalogExamples/orders_tire_first.json`).
- Где находится колесо (машина, руки, станок) — состояние игры, а не данные каталога; в JSON его не задают.
